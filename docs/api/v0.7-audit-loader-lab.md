# v0.7 audit, firmware corpus, and loader laboratory

Snapshot date: 2026-08-23

Static-analysis addendum: 2026-08-25

Version 0.7 adds API infrastructure that can be completed safely without stove
hardware. It does not add human-facing commands and it does not enable physical
firmware programming.

## Exact-byte audit API

`AuditTrail` is a presentation-neutral recorder. It retains the exact chunks
offered to and returned by a transport, timestamps each event, and can flush
every event immediately to a JSONL file. A checkpoint isolates one workflow's
traffic from the rest of a long-lived controller session:

```python
from openmaxfire import AuditTrail, ControllerSession

audit = AuditTrail("bench-session.jsonl", metadata={"purpose": "read-only"})
with ControllerSession.connect("/dev/ttyUSB0", audit=audit) as session:
    start = audit.checkpoint()
    value = session.read_register(0x02)
    receipt = audit.span(start)
```

`AuditSpan.sha256` hashes direction, byte length, and bytes—not wall-clock
timestamps—so two byte-identical exchanges have the same evidence digest.
Audit spans are included directly in structured control, configuration,
Checkout, and loader results when a session/workflow has an audit trail.

## Firmware corpus API

`FIRMWARE_CORPUS` now describes five preserved PIC16F877A images. Version 0.7
introduced the original four-entry catalog; the recovered 2.02 original-chip
read was added later without changing the validation contract:

| Firmware | Variant | Program words | Configuration word |
| --- | --- | ---: | --- |
| 2.02 | Original PICkit read | 8,192 | `3F32` |
| 2.06 | Downloader | 7,599 | `3F76` |
| 2.06 | PICkit | 8,192 | `3F32` |
| 2.70 | Embedded Downloader image | 7,681 | `3F72` |
| 2.71 | Embedded Downloader image | 7,755 | `3F72` |

`validate_firmware_corpus(repo_root)` fails closed on a missing file, Intel HEX
parse error, checksum error, hash/size mismatch, inferred version/variant
mismatch, program-word-count mismatch, or configuration-word mismatch. CI runs
the same public API over the repository's preserved corpus.

## Loader plan and state machine

`build_loader_plan(image, profile)` combines strict Intel HEX parsing,
controller compatibility, sparse-aware PIC word grouping, and reconstructed
binary frames. The current plan API distinguishes ordinary offline plans from
an `authenticated_simulator_plan`; neither enables hardware writes. Serialized
plans report `physical_e3_enabled: false` and state that physical programming
is hard-disabled.

The simulator-only executor models this established sequence:

| State | Host | Reconstructed controller response |
| --- | --- | --- |
| Identify | `EA` | `EB`: loader identified |
| Program block | `E3`, address high/low, byte count, data checksum, 2-32 data bytes | `E7`: checksum accepted; `E4`: PIC write/readback succeeded |
| Complete | `ED` | `E4`: completion acknowledged |

The PIC returns `E8` for a received-payload checksum mismatch and `E5` when its
write or readback verification fails. The v0.7 simulator still models only the
expected successful `E7`, `E4` sequence and generic acknowledgement failure.

Each exchange is currently bounded by `LoaderPolicy.max_retries` (default 30
retries in addition to the initial attempt). Later static analysis established
that BixCheck accepts at most 30 total attempts. Its loop can transmit a 31st
block frame but aborts before accepting that response. The simulator therefore
has an accepted-attempt budget one larger than BixCheck and should be corrected
in a later API change.

A result contains completed-block count, total retries, per-block
attempts/acknowledgements, final simulated-memory comparison, message, and exact
audit span. `memory_verified` describes comparison against simulated memory;
it is not evidence of a physical host-side program-memory readback.

```python
from openmaxfire import (
    AuditTrail,
    FirmwareImage,
    PROFILES_BY_KEY,
    SimulatedLoaderTransport,
    build_loader_plan,
    execute_loader_plan,
)

image = FirmwareImage.load("Bixby_0271_080315.hex")
plan = build_loader_plan(image, PROFILES_BY_KEY["fw271-format07"])
audit = AuditTrail()
result = execute_loader_plan(
    SimulatedLoaderTransport(),
    plan,
    authorize=True,
    audit=audit,
)
assert result.successful
```

The executor checks the exact concrete transport type and rejects serial
transports, simulator subclasses, recording wrappers, and duck-typed
substitutes with
`CapabilityUnavailableError`. Authorization is mandatory even in simulation.
The PICkit image is not eligible for J3 loader planning. The recovered J3
Downloader images contain no data-EEPROM words. The resident loader also skips
direct targets at and above `0x1E80` and redirects application addresses
`0x0000` through `0x0003` to its reset trampoline at `0x1E84` through `0x1E87`.
Those protection and relocation rules are not yet modeled by v0.7.

## Fault and recovery coverage

The isolated loader simulator can inject:

- missing/bad identify acknowledgements;
- address-specific block failures;
- completion failures;
- disconnects after a selected accepted-block count;
- accepted data that is silently corrupted before final comparison.

The normal controller simulator can disconnect after an exact request count.
This establishes that a connection loss after a control/configuration write
returns `indeterminate`/`failed` plus exact evidence; it never returns verified.
Checkout cleanup failure remains explicitly visible in its structured result.

## Deliberately absent live behavior

The API still does not provide:

- `CW0FC4` bootloader entry;
- a physical loader serial transport;
- physical four-word row erase/write execution;
- explicit `E5` and `E8` failure classification;
- PIC-side partial-row preservation and readback modeling;
- physical program-memory readback/verification;
- post-transfer reset/reconnect;
- interrupted physical-transfer recovery.

There is no standalone whole-chip erase command or erase acknowledgement in
the reconstructed J3 protocol. The PIC performs erase and write together for
each four-word Flash row.

Those gaps require a sacrificial, externally recoverable controller. The
offline state machine is a laboratory for validating them, not permission to
flash the installed heating controller. See the [complete protocol
reconstruction](../reverse-engineering/bixcheck-downloader-protocol.md).
