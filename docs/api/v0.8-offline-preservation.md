# v0.8 offline loader fidelity and firmware preservation

Snapshot date: 2026-08-27

Version 0.8 completes the evidence-backed loader behaviors that can be modeled
without hardware and prepares a read-only PICkit preservation workflow. It
does not add physical loader entry, serial flashing, programmer control, or a
high-level physical normal-control executor.

## Loader simulator fidelity

The simulator now models:

- distinct `E8` payload-checksum rejection and `E7` then `E5` PIC
  write/readback failure receipts;
- four-word Flash rows, partial-row neighbor preservation, PIC-side readback,
  and up to two internal row-write attempts;
- relocation of source words `0x0000`-`0x0003` to the protected application
  trampoline at `0x1E84`-`0x1E87`;
- successful skipping of other direct targets at or above `0x1E80`;
- 30 block attempts whose responses BixCheck can accept, followed by the
  reconstructed 31st transmission whose response is not accepted;
- one-shot `ED`/`E4` completion, application handoff, and a fail-closed
  in-memory reconnect state;
- exact attempt receipts, response classification, row attempts, memory
  comparison, preservation checks, audit bytes, and injected interruption.

The identify loop remains bounded by policy in simulation so tests cannot run
forever. The physical BixCheck UI instead continues probing the reset window
until it identifies, is cancelled, or otherwise exits.

`memory_verified` still means comparison against simulator state. `E4` proves
only the loader's local PIC-side block readback; neither is a physical
whole-device readback.

## Format-04 state evidence

Reanalysis of the preserved physical control session established that `T09=07`
was constant before ON, during physically observed UP/DOWN startup activity,
and after OFF. It is therefore explicitly non-discriminating on firmware 2.02,
not an off-state value.

The monitor exposes two provisional composite observations from the same
capture:

| Raw composite, ignoring validated thermostat bit `T0C.3` | Candidate |
| --- | --- |
| T0C base `20`, T15 `0F` | Cold/off candidate |
| T0C base `30`, T15 `08` | Startup/control-active candidate |

Both carry `control_verification_eligible=false`. `operating_state`, current
level, and target level remain unset for format 04, so this evidence cannot
unlock physical high-level control.

## PICkit read-export authentication

`inspect_pic16f877a_dump()` and `compare_pic16f877a_dumps()` parse programmer
HEX exports and compare normalized program memory, all 256 data-EEPROM bytes,
four User ID words, and the configuration word. Reports include raw and
section-level SHA-256 values, PIC16F877A Device ID checks when present, and CP/
CPD protection status.

Enabled or unknown code protection, absent program/EEPROM content, a wrong
device ID, or any section difference fails closed. The companion
`tools/pickit_preservation.py` writes a machine-readable manifest but has no
hardware connection, erase, or programming capability.

The complete operator workflow is in the
[PICkit 3 read-only preservation guide](../guides/pickit3-firmware-preservation.md).
The project procedure requires three independently power-cycled original-chip
reads before programming any spare.

## Still blocked

- physical `CW0FC4`, `EA`, `E3`, or `ED` execution;
- physical Flash erase/program/readback and timing;
- a programmer-control API;
- clearing or bypassing code protection;
- enabling normal control from provisional format-04 candidates;
- installing a clone before its readback and controlled board validation.
