# Version 0.5 Python API foundations

Snapshot date: 2026-08-23

This is the reusable machine-facing API milestone. It adds no human-friendly
commands, GUI controls, or Home Assistant entities. Those clients must consume
these objects rather than reproduce controller logic.

## Public modules

| Module | Stable foundation in v0.5 | Hardware I/O |
| --- | --- | --- |
| `profiles` | Four exact firmware/data-format profiles, register meanings, baud rates, capabilities | None |
| `discovery` | Read-only candidate-port and 9,600/19,200-baud probing, explicit result status | Identity reads only |
| `models` | Typed panel, physical-input, alarm, telemetry, and stove snapshots | None |
| `monitor` | Profile-aware decoding, freshness, raw preservation, capture replay | Existing read-only poller |
| `control` | Idempotent OFF/ON/UP/DOWN/set-level plans and outcome vocabulary | Plans only; execution blocked |
| `configuration` | EEPROM images, checksum validation, format-05/07 schemas, edits, diffs, update/restore plans | Plans only; execution blocked |
| `checkout` | All 45 reachable BixCheck tests, passive predicates, action/cleanup plans, report types | Actuator execution blocked |
| `firmware` | Intel HEX validation, PIC14 mapping, delivery variants, compatibility reports, E3 blocks | Loader execution blocked |
| `simulator` | API-compatible controller/transport/factory and deterministic faults | None |
| `errors` | Common catchable exception taxonomy | None |

Existing `protocol`, `transport`, `client`, `transactions`, and `backup` modules
remain the low-level base. The CLI is a consumer; it is not part of this API
milestone.

## Detection and profile negotiation

```python
from openmaxfire import detect_controllers

report = detect_controllers(["/dev/ttyUSB0"])
result = report.results[0]
if result.supported:
    profile = result.profile
    print(profile.key, profile.capabilities.to_dict())
```

Detection only sends the established identity reads. A valid but unknown
identity is returned as `unsupported`; it is never silently treated as a known
controller. A timeout remains distinct from malformed traffic and transport
failure.

## Typed monitor state

`decode_stove_snapshot()` takes one explicit profile plus raw C/T/status maps
and returns an immutable `StoveSnapshot`. It always retains the raw bytes.
Format 04 uses only correlations preserved on the live 2.02 controller; it does
not reuse later-format meanings merely because an address matches. Format 05/07
uses the recovered BixCheck conversions and still leaves unknown physical units
unset.

## Configuration images and plans

```python
from openmaxfire import ConfigurationImage, plan_configuration_update

current = ConfigurationImage.from_backup_document(backup_json)
updated = current.edit({"fuel_a_fan_level_1": 42})
plan = plan_configuration_update(current, updated, profile)
print(plan.to_dict())
```

The format-05 schema contains the recovered 71 adjustments and format 07 the
recovered 82. Shared bit fields are merged without clobbering neighbors and
lean-burn values use BixCheck's wire transforms. Identity bytes are read-only
unless an expert caller explicitly overrides that rule.

Plans write changed A bytes and then request `CW0100`; firmware recomputes and
persists A00/A01. The verification contract is a fresh read of all A00-AFF,
not same-address write echo. `execution_supported` remains false until the
sequence has been tested on recoverable hardware with a mandatory pre-write
backup.

Formats 00-04 deliberately expose identity-only schemas. Format-04 adjustment
labels cannot be safely inferred from the later BixCheck tables.

## Checkout catalog

`CHECKOUT_TESTS` contains exactly the 45 reachable BixCheck tests. Passive
expectations are machine-evaluable. State-changing plans publish exact known
commands, timeout metadata, and cleanup when reconstructed, but stay blocked if
the action is incomplete, cleanup is unavailable, or the profile lacks a
validated actuator capability. Merely transmitting a command is never a pass.

## Firmware images and loader boundary

`FirmwareImage` validates Intel HEX checksums, rejects overlapping or invalid
records, enforces PIC14 program-word width, distinguishes Downloader/PICkit/
embedded layouts, and reports target and data-format compatibility.
`build_program_blocks()` constructs the recovered E3 frames in blocks of at
most 16 PIC words.

There is intentionally no erase/program executor. `loader_state_machine_supported()`
returns false because acknowledgement meaning, verification, and interrupted-
transfer recovery have not been proven. PICkit images are rejected as J3
delivery layouts. Program-memory dumping over J3 remains unsupported; no such
command has been found.

## Control and safety boundary

`plan_control()` avoids redundant commands, rejects stale or wrong-profile
snapshots, and produces bounded UP/DOWN sequences for an explicit heat level.
Plans remain non-executable because no OFF/ON/UP/DOWN write has yet been
physically validated. Future executors must return one of the structured
outcomes and verify a fresh resulting state; transmission alone means only
`sent`.

All state-changing APIs must add authorization, bounded timing, exact traffic,
profile/state checks, verification, and unconditional cleanup before their
capability can become `available`.
